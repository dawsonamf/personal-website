Problem. layoutFor returns only the layout; the same skin / owned / fallback / utility branch is re-derived by ThemeAssets (asset set) and the Shell (FAB, canonical/noindex): one feature check in three shared files.

Solution. compose.ts returns one composition value (layout, asset set, picker mount and corner, canonical URL and robots flag, theme-less path); Shell, ThemeAssets and PickerFab render it and never read theme.kind or theme.picker.

  • locality: one function holds the rule
  • leverage: eight readers, one value
  • test surface: one table test, kinds × page types
  • structural themes learn one fact set

Deletion test: delete compose.ts and the branch reappears in five page files, the Shell and ThemeAssets. Concentrates.

Top recommendation

Candidate 1, decide the composition once. It is the seam every one of the five future themes crosses, and the fix is spec text before any code exists. Candidate 2 rides along in the same §5 rewrite and must land before T3, because T5's DOM diff will otherwise fail on every themed post page.

Verdict: the spec's architecture is in good shape. Build/runtime seam where intent §4 puts it, acyclic module graph enforced by imports, accessor / href / markdown / registry / settle / normalize deep as specified. Friction concentrates in three places: a composition decision re-derived in three shared files; a head position the current pages contradict on posts; three kept-verbatim mechanisms (ticker, masthead steps, seven globals) carrying build-time facts through runtime feeds because D3 froze the scripts before the render/behavior line was drawn. No card conflicts with an intent §4 decision; two touch D14 and D29 where the friction is real; one (D3) is deferred on purpose.
