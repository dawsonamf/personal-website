# Spec 1 review — axis: correctness

**Reviewer:** 04-correctness-opus-1
**Spec:** `docs/intents/2026-09-05-theme-engine-rewrite/spec-1-migration-engine-parity.md` (902 lines)
**Baseline:** `main` @ `0f196d0`
**Question answered:** if an implementing agent follows this spec literally, does the result do what the intent requires, and is every claim the spec makes true?

Third-party facts were verified against primary sources (docs.astro.build, the `astro@7.3.1` source, Playwright `v1.61.1` type definitions, `npm view`, docs.github.com, nodejs/Release `schedule.json`). Codebase facts were verified against the files at `0f196d0` with `file:line` quotes.

Headline: the spec is unusually accurate on facts — of ~120 checkable claims, the great majority hold exactly, including several the reviewer expected to fail (mermaid's 76.3 MB / 3.3 MB, boxicons' six deps, highlight.js `lib/common`'s 36-language set matching cdnjs byte-for-byte, the ×12 marquee ticker repeat, all four GitHub Action versions, the Node release dates, and the "Sätteri" package name). The problems are concentrated in **three places**: the post DOM contract, the parity harness's inability to express its own allow-list, and a pre-paint behavior the spec asserts does not exist.

## Blockers

### C-01 — §7's post DOM contract omits three classes that 20 skin sheets target
- **severity:** blocker · **confidence:** high
- **spec lines:** 542-544 (§7 "Body"), 106 / 616 (harness), 772 (T3), 774 (T5)
- **spec says:** "`article.blog-post-container > header.blog-post-header > h1#post-title + div#post-meta` (pills: date, tags, `span#read-time`) + `div#post-content` with the rendered HTML, **exactly today's DOM**".
- **evidence:** the three inner elements carry classes as well as ids. `blog/post.html:87-93` renders `h1` with class `blog-post-title`, the meta `div` with class `blog-post-meta`, and the content `div` with class `blog-post-content`. Skin sheets target the classes, not the ids: `.blog-post-content` appears in **20** of the 20 files in `css/themes/`, `.blog-post-title` in **17**, `.blog-post-container` in 8, `.blog-post-meta` in 6, `.blog-post-header` in 6.
- **what is wrong:** an implementer reproducing precisely what §7 specifies emits `<h1 id="post-title">`, `<div id="post-meta">`, `<div id="post-content">` and loses `.blog-post-title`, `.blog-post-meta`, `.blog-post-content`. Every skin's post-page typography, spacing and rules silently revert to the canonical sheet. §7 is the only place the post DOM is specified, and it names the container/header classes but not these three — the asymmetry reads as deliberate.
- **correct statement:** the post body is `article.blog-post-container > header.blog-post-header > h1#post-title.blog-post-title + div#post-meta.blog-post-meta`, then `div#post-content.blog-post-content` as a sibling of the header inside the article; all five classes are part of the parity surface.

### C-02 — §9 defines parity as exact DOM equality but provides no mechanism for the allow-list §15 exists to be
- **severity:** blocker · **confidence:** high
- **spec lines:** 16 and 841 (§15 called "the harness allow-list"), 601-604 (parity definition), 658-675 (the 7-step normaliser), 773-775 (T4/T5/T6 "Done when: harness green")
- **evidence:** §9 item 1 is `expect(newLines).toEqual(oldLines)` — exact array equality. The normaliser's seven steps drop `<script>`/`<noscript>`/`<link rel=modulepreload>` (step 2), strip `data-astro-*` (step 3), lowercase/sort/collapse (4-5), rewrite old link forms (6), and drop `--prose-*` from `<html style>` (step 7). Nothing else is removed: step 2 says so explicitly ("Nothing else is removed, so `<head>` order is compared as-is"). Grep for "allow-list" in the spec returns four hits: line 16, line 612 (`harness/scripts.ts`, a *`<script src>`* allow-list — a different check), line 775 ("with the FAB allow-listed"), line 841.
- **what is wrong:** at least four of §15's eleven deliberate changes produce DOM that the normaliser cannot reconcile, so checks 1 and 2 fail by construction:
  - §15.3 the `PickerFab` on privacy/404/lexchat — a new element with no counterpart on the old side. T6 says "with the FAB allow-listed" but no allow-list exists to list it in.
  - §15.4 post pages gain `<meta name="description">`, `<link rel="canonical">` and five OG tags. §6.2 line 490 confirms the old post page has none of these. (The JSON-LD survives via step 2; `<title>` matches after settle because `blog-post.js` sets it. The meta and link tags do not.)
  - §15.10 themed pages gain `<link rel="canonical">` + `<meta name="robots" content="noindex">` on all 15 non-default theme path sets, on every page type.
  - §15.9 the dock is server-rendered with prose in `data-*` attributes; step 6 rewrites the preset-row `href`s but nothing accounts for new `data-*` attributes that the old JS-built dock does not carry.
- **correct statement:** §9 needs an eighth normaliser step (or a per-URL exception table) that enumerates §15's changes by selector, and checks 1-3 must be defined as "equal after applying the §15 exception table"; otherwise T4/T5/T6's "Done when: harness green" is unsatisfiable.

### C-03 — D4's "there is no pre-paint override today and none is added" is false, and retiring the bootstrap introduces an unlisted colour flash
- **severity:** blocker · **confidence:** high
- **spec lines:** 51 (D4), 843-844 (§15 items 1-2), 629-630 (§9 "Fresh browser context per test")
- **spec says:** "The palette toy keeps restoring after load as it does today (`theme-cycler.js:126-147`); **there is no pre-paint override today and none is added.**"
- **evidence:** `js/theme-bootstrap.js:727-742` — inside the synchronous, parser-blocking `<head>` script, before any paint:
  ```js
  var colors = entry.colors;
  if (THEME_CYCLER_ENABLED) { try {
      if (isReload) { sessionStorage.removeItem(STORAGE_KEY); }
      else { var raw = sessionStorage.getItem(STORAGE_KEY);
             if (raw) { var saved = JSON.parse(raw);
               if (saved && Array.isArray(saved.colors) && saved.colors.length === 5) {
                 colors = { text:saved.colors[0], bg:saved.colors[1], ... }; } } }
  } catch (e) {} }
  ```
  `colors` then feeds the ramp at `:764-774`. The palette toy's session colours are therefore applied **pre-paint** on every navigation today. The cycler's `restore()` (`theme-cycler.js:142-154`, called from `boot()` at `:748-752`, script loaded `defer`) is a *post-load* re-application on top of an already-correct paint.
- **what is wrong:** D4 retires `theme-bootstrap.js` and emits the theme's **default** colours into the build-time inline style. With a live toy session, every page now paints the default palette and then flips to the visitor's palette after `defer` scripts run. That is a new flash on every internal navigation. D11/Q12 make it worse by extending toy state across reloads, where today the wipe (`theme-bootstrap.js:687`, `:730-731`) prevents any flash. The flash is not in §15, and §9's "Fresh browser context per test" guarantees empty sessionStorage, so the harness never enters this state at all (see C-19).
- **correct statement:** the bootstrap applies the palette-toy session pre-paint (`theme-bootstrap.js:727-742`); either `ThemeRuntime`'s inline script must read `dawson-theme-cycler` and re-stamp the ramp before paint (which reintroduces the blocking script D4 removes), or the resulting flash must be added to §15 and accepted.

### C-04 — D30's picker trigger contract is wrong; the FAB as specified cannot be opened on mobile
- **severity:** blocker · **confidence:** high
- **spec lines:** 77 (D30), 59 (D12), 386-387 (§5.2), 730-731 (§11), 775 (T6), 617-619 (§9 matrix includes mobile-390 and "theme menu open by click")
- **spec says:** "any `.tc-nav-item` element **is** a trigger (the cycler's selector today) ... `PickerFab.astro` renders a fixed `.tc-nav-item.tc-fab`".
- **evidence:** `.tc-nav-item` is the container `<li>`, not the trigger. `theme-cycler.js:558-559` collects containers (`document.querySelectorAll('.tc-nav-item')`; early-return if none — this part of D12 is correct). The **click** handler binds a different selector, `.tc-nav-trigger` (`theme-cycler.js:601`, `:686`), which `js/nav-config.js:101` emits as a child: `const cls = (item.icon ? 'socials-item' : 'menu-item') + ' tc-nav-trigger';`. Hover-open binds on the `.tc-nav-item` but is gated by `theme-cycler.js:594`: `const canHover = window.matchMedia('(hover: hover) and (pointer: fine)').matches;`.
- **what is wrong:** a `PickerFab.astro` that renders only `.tc-nav-item.tc-fab` gets hover-open and no click-open. On the 390 viewport in §9's matrix — and on every real phone — `canHover` is false, so the FAB does nothing at all. This defeats intent §4.7 ("The global theme picker must be reachable in every theme") on exactly the pages D12 exists to fix, and §9's "theme menu open by click (pages with a trigger)" state would fail on privacy/404/lexchat.
- **correct statement:** a picker mount is a `.tc-nav-item` container wrapping a `.tc-nav-trigger` clickable; `PickerFab.astro`, `ThemePicker.astro` and the canonical Nav must all emit both, and D30 should read "any `.tc-nav-item` hosting a `.tc-nav-trigger`".

## Majors

### C-05 — §4.1's `titleSuffix` rule is false for two of the six page types
- **severity:** major · **confidence:** high · **spec line:** 183
- **spec says:** `titleSuffix: { xs: Dawson Metzger-Fleetwood }   # "<title> | <suffix>" on every page`
- **evidence:** `index.html:6` → `<title>Dawson Metzger-Fleetwood</title>` (no suffix); `lexchat/index.html:6` → `<title>LexChat</title>` (no suffix). The other four do use it: `privacy/index.html:6` "Privacy Policy | …", `blog/index.html` "Blog | …", `404.html` "404 | …", `blog/post.html` "Loading… | …".
- **what is wrong:** applied literally with `meta.home.title.s = "Dawson Metzger-Fleetwood"`, home becomes "Dawson Metzger-Fleetwood | Dawson Metzger-Fleetwood" and lexchat becomes "LexChat | Dawson Metzger-Fleetwood". `<title>` is inside the DOM dump (step 2 drops only script/noscript/modulepreload), so this is both a visible and a harness-visible break.
- **correct statement:** the suffix applies to blog, post, privacy and 404; home and lexchat use their title verbatim.

### C-06 — §6.2, §6.3, D2 and §9 step 3 contradict each other on the 404 page's `<style>`
- **severity:** major · **confidence:** high · **spec lines:** 492-494 (§6.2), 500 (§6.3), 49 (D2 `inlineStylesheets: 'never'`), 665-666 (§9 step 3)
- **evidence:** §6.2: "**No component `<style>`** and no frontmatter CSS imports anywhere in the canonical family: Astro's injection position is undocumented, so the family gives it nothing to inject." §6.3: "`404.astro` … keeps its `.nf-*` rules in an inline `<style>` as today." `404.html:18-40` does hold an inline `<style>` with `.nf-container`, `.nf-code`, `.nf-text`.
- **what is wrong:** three-way conflict. A plain `<style>` in a `.astro` file is a component style, which (a) contradicts §6.2's premise, (b) under D2's `build.inlineStylesheets: 'never'` is extracted to an external `/_astro/*.css` `<link>` rather than staying inline, which in turn contradicts §9 step 3's "the canonical family should emit none [of `/_astro/`]", and (c) gets scoped, adding `data-astro-cid-*` to the selectors and raising their specificity against the skin sheets that also style `.nf-*` (5 sheets: `banknote, constructivist, gallery, grid, neo-pop`).
- **correct statement:** `404.astro`'s `<style>` must carry `is:inline`; §6.2 should say "no *processed* component `<style>`" and name the 404's `is:inline` block as the single exception.

### C-07 — D7's "one content-collection entry" only holds if the `parser` wraps the document
- **severity:** major · **confidence:** high · **spec lines:** 54 (D7), 277-278 (rule 6), 57 (D10)
- **spec says:** "One YAML document loaded as **one** content-collection entry via `file()` + `parser`, so one zod tree validates it and one `superRefine` lists every draft at once."
- **evidence:** `astro@7.3.1`, `packages/astro/src/content/loaders/file.ts`: for non-array data, `const entries = Object.entries(data); for (const [id, rawItem] of entries) { … store.set({ id, … }) }`. A top-level YAML mapping therefore becomes **one entry per top-level key**. The `parser` option is real (`parser?: (text: string) => ParserOutput`) but a plain `parser: (t) => yaml.load(t)` yields ~17 entries (`site`, `meta`, `nav`, `socials`, `home`, `jobs`, `projects`, `posts`, `post`, `carousel`, `blog`, `canonical`, `picker`, `themes`, `privacy`, `notFound`, `lexchat`).
- **what is wrong:** with 17 entries, zod validates each separately and D10's guarantee ("all are reported at once", line 277-278) collapses into exactly the per-section failure mode §4.1 cites `research/astro-capabilities.md` §2.2 to avoid. The spec never states the loader's default splitting behavior, so an implementer has no reason to add the wrapper.
- **correct statement:** the parser must wrap the document in a single key — `parser: (t) => ({ prose: yaml.load(t) })` — otherwise `file()` emits one entry per top-level key and the single-`superRefine` guarantee is lost.

### C-08 — §4.1's `jobs[].id` invents ids the jobs panel does not use
- **severity:** major · **confidence:** high · **spec lines:** 213 (`- id: about-objects`), 64 (D17), 618 (§9 state "job tab 2 clicked")
- **evidence:** the jobs panel keys off `job-N`, not a slug: `index.html:153` renders the nav item with `data-job="job-N"` and the panels carry `id="job-1"`…`id="job-4"`; `js/script.js:273` reads `document.getElementById("highlight")` and `moveHighlight` (`:283-302`) measures the element matched by `data-job`.
- **what is wrong:** D17 specifies what a job's *prose* is ("`role` + `company` (+ url)") but never says the DOM ids stay `job-N`. An implementer emitting `id={job.id}` from the prose entry breaks tab switching and the measured highlight bar — a behavior §9 does test ("job tab 2 clicked"), so it would be caught, but only after the work is done wrong.
- **correct statement:** `prose.jobs[].id` is a content key only; the canonical Jobs component must keep emitting `id="job-{i+1}"` and `data-job="job-{i+1}"` in source order.

### C-09 — §6.2 undercounts the home page's social meta tags

### C-11 — §10's cutover produces an add/add merge conflict on `deploy.yml`
- **severity:** major · **confidence:** high · **spec lines:** 704-705 (step 2), 713-714 (step 6), 834 (§14 item 4), 776 (T7)

### C-12 — `gemma4-heretic-ara` deadlocks the build between schema rule 3, the draft gate and §15.4
- **severity:** major · **confidence:** medium-high · **spec lines:** 272-273 (rule 3), 277-278 (rule 6 / D10), 537-540 (§7 post head), 847-848 (§15 item 4), 803 (Q2 default)

### C-15 — §8's "defer everywhere" is wrong for three of the six pages

### C-16 — §5.5 converts `injectDom()` but not the three other functions that build dock DOM
- **severity:** major · **confidence:** high · **spec lines:** 411-412 (§5.4), 449-452 (§5.5)

### C-17 — D18 reverses a locked intent decision without citing it
- **severity:** major · **confidence:** high · **spec line:** 65 (D18), 88 (§3.1 tree); intent §4.10
- **evidence:** intent §4.10 (locked): "`CNAME` and `.nojekyll` ride in `public/`." D18: "`CNAME` and `.nojekyll` stay at the repo root … and are **not** put in `public/`."

- **severity:** major · **confidence:** high · **spec lines:** 830-831 (§14 item 3), 69 (D22)

### C-19 — the harness never enters the palette-toy state that §15 item 2 introduces
- **severity:** major · **confidence:** high · **spec lines:** 629-630, 683-686 (manual QA), 844 (§15 item 2)
- **evidence:** "Fresh browser context per test" means `sessionStorage` is empty on every run, and no state in the §9 matrix seeds `dawson-theme-cycler` (`theme-cycler.js:124`). The manual QA list covers the toy's *interaction* ("palette toy shuffle/scheme/lock/colour input") but not a subsequent navigation or reload with the toy active.
- **what is wrong:** §15 item 2 is an explicitly listed behavior change with no automated coverage and no manual QA step. Combined with C-03 this is the specific hole through which the flash ships.
- **correct statement:** add a matrix state that shuffles the palette, navigates, and asserts the paint; or add "navigate and reload with an active palette" to the manual QA list.

## Not verified

1. **`compressHTML: false` yields byte-identical whitespace to hand-written HTML.** The default and the semantics are confirmed, but whether the Rust compiler's output for a ported `index.html` is byte-equal cannot be checked without building. This is T0 item (a)/(b) and is correctly marked as a spike.
2. **The inline `<html style>` is reproducible byte-for-byte.** The old side's string is produced by CSSOM serialization of ~100 `setProperty` calls; the new side is a build-time string. Custom properties are stored as unparsed token streams, so it is very likely achievable, but only a build can confirm. See C-33 for the ordering caveat.
3. **Whether a throw in `astro:build:done` exits non-zero.** Docs are silent; `astro@7.3.1`'s `integrations/hooks.ts:75-98` wraps the hook in no try/catch, so a throw should propagate, but this is not documented. The spec's `process.exit(1)` fallback (D10) is the right hedge.
4. **Whether `upload-pages-artifact` succeeds while Pages source is still legacy.** No GitHub doc addresses it (see C-31).
5. **Whether Sätteri's markup differs from marked's.** D6 sidesteps the question by not using Astro's pipeline, which is the safe call; the comparison itself was not made and does not need to be.
6. **The five sha256 prefixes in `research/library-migration.md` §1** and the one-byte `jquery-ui` difference. Verifying would require downloading tarballs and the CDN copies and hashing both; the package paths were confirmed to exist (all 200) but the bytes were not compared. T4 is specified to record them.
7. **`prose:check` under Node 24's native type stripping.** Type stripping is on by default from Node 22.18, but whether `src/prose/check.ts` runs depends on details the spec does not fix (relative imports need explicit `.ts` extensions; tsconfig `paths` aliases like the `~/prose` shown in §4.2 are not resolved by bare `node`). Flagged as a risk, not a finding, because §4.3 scopes `check.ts` to the pure walker in `drafts.ts`, which needs only js-yaml.
8. **Screenshot thresholds.** Whether `maxDiffPixelRatio: 0.001` / `threshold: 0.2` are tight enough to catch the flash in C-03 or loose enough to avoid font-rendering false positives is empirical; intent §9 leaves thresholds open and the spec picks values without justification. Not checkable without a run.
9. **The five research files' internal accuracy** beyond the specific sections the spec cites for the claims above. Only cited claims were traced back to code.
